# Release checklist (MKB-016)

Этот проект — один Node-процесс на polling (`npm start` / `npm run dev`), без HTTP-сервера
и без CI на данный момент. Релиз = обновить код на сервере, применить новые миграции,
перезапустить процесс.

## Перед релизом

1. `npm run check` (`format:check` + `lint` + `build` + `test`) — обязателен, это же
   выполняет pre-commit hook (`.husky/pre-commit`) перед каждым коммитом.
2. Просмотреть `git log` со времени последнего релиза — какие тикеты вошли, есть ли
   новые файлы в `sql/`.
3. Резервная копия БД перед любой миграцией:
   ```bash
   pg_dump "$DATABASE_URL" -F c -f backup_$(date +%Y%m%d_%H%M%S).dump
   ```
4. На тестовой/локальной копии БД прогнать `npm run migrate:up` — миграции должны
   применяться и на чистой базе, и повторно на уже обновлённой (все миграции в проекте
   идемпотентны: `IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`).

## Выкладка

1. Остановить текущий процесс бота (SIGTERM — обработчик в `src/index.ts` корректно
   закрывает пул соединений и завершает polling).
2. Обновить код (`git pull` / деплой артефакта).
3. `npm ci && npm run build`.
4. `npm run migrate:up` — применяет все файлы из `sql/` по порядку. Смотреть вывод: если
   какой-то файл упал, это почти всегда означает, что он перестал быть идемпотентным —
   останавливаться и разбираться, не запускать вручную «руками», не игнорировать ошибку.
5. Запустить процесс (`npm start`), проверить лог на `"Bot is running."` и отсутствие
   ошибок подключения к БД/курсам валют.
6. Смоук-проверка в Telegram (см. ниже) под собственным аккаунтом.
7. `/health` (только для `ADMIN_TELEGRAM_ID`) — БД отвечает, курсы валют не «устаревший».

## Смоук-проверка после релиза

- `/start` → видно главное меню с кнопками.
- Быстрый ввод: `25 GEL тест` → бот предлагает категорию → сохранение → виден остаток и
  кнопка «Отменить» → отменить.
- `/today`, `/month` → суммы совпадают со здравым смыслом, есть кнопки меню под ответом.
- `📋 Дашборд`, `📈 Статистика`, `📉 Тренд` → открываются, переключение периода работает.
- `/settings` → смена валюты отображения и часового пояса, `/settings reset`.
- `/payments`, `/goal` → списки открываются, пауза/возобновление платежа работает.

## Откат миграций

В проекте нет инструмента миграций с автоматическим down — каждый файл в `sql/`
обратим только вручную. Ниже — что реально отменяет каждый файл (только для
экстренного отката; обычная последовательность отката — восстановить `pg_dump` из шага
«Перед релизом», а не откатывать миграции по одной).

| Файл | Откат |
| --- | --- |
| `schema.sql` | `DROP TABLE transactions` — уничтожает все операции, только для полностью пустой БД |
| `002_add_rate_cache.sql` | `DROP TABLE rate_cache` |
| `003_recurring.sql` | `DROP TABLE recurring` — таблица уже не используется кодом (см. коммит с удалением `src/recurring.ts`) |
| `003_release_0_0_8.sql` | `DROP TABLE categories, budgets, recurring_payments, savings_goals` |
| `004_categories_rules.sql` | `ALTER TABLE categories DROP COLUMN kind; ALTER TABLE budgets DROP COLUMN rollover` |
| `005_savings_goal_target_date.sql` | `ALTER TABLE savings_goals DROP COLUMN target_date` |
| `006_user_settings.sql` | `DROP TABLE user_settings` |

## Известные ограничения

- Нет CI — `npm run check` запускается только локально/вручную перед коммитом (через
  Husky pre-commit) и перед релизом по этому чек-листу. Если появится CI, тот же
  `npm run check` — единственная команда, которую нужно туда воткнуть.
- Нет staging-окружения и тестовой БД в CI (см. `docs/SECURITY_AUDIT.md`) — releases
  проверяются вручную по смоук-чек-листу выше.
- `/health` — не HTTP health-check, а команда в Telegram; годится для ручной проверки
  после релиза, не для автоматического мониторинга/аптайма.
