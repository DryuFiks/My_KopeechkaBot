# Security & E2E audit (MKB-015)

Согласовано с пользователем: вместо тестовой Postgres/testcontainers и полноценных
E2E-тестов — аудит существующего кода (подтверждающий, что защита реально есть, а не
просто подразумевается) плюс чек-лист ручной проверки. В проекте нет CI и нет
Docker-инфраструктуры; добавление их — отдельная по объёму задача, не часть этого
чек-листа.

## Изоляция по user_id

Проверен каждый SQL-запрос, касающийся таблиц с пользовательскими данными
(`transactions`, `budgets`, `categories`, `recurring_payments`, `savings_goals`,
`user_settings`) — в `src/db.ts`, `src/db/budget.ts`, `src/db/payments.ts`,
`src/db/goals.ts`, `src/db/settings.ts`, и оставшиеся прямые `pool.query` в
`src/features/*.ts`/`src/handlers/**/*.ts`.

**Результат: без замечаний.** Каждый запрос к пользовательским данным фильтрует по
`user_id`, полученному из `ctx.from.id` (аутентифицированный Telegram-пользователь), а
не из пользовательского текста или callback_data.

Два запроса не фильтруют по `user_id` намеренно — оба внутренние, вызываются только
планировщиком напоминаний (`src/reminders.ts`), никогда напрямую командой/кнопкой
пользователя:
- `getRemindablePayments()` (`src/db/payments.ts`) — по определению должен видеть
  платежи всех пользователей, чтобы разослать напоминания.
- `markPaymentNotified(id)` — `id` берётся не из ввода пользователя, а из строки,
  только что прочитанной тем же планировщиком из БД.

### Callback-data с id: проверка на подбор чужого id

Отдельно проверено: может ли пользователь, подставив чужой id в callback_data
(`undo:<id>`, `delpay:<id>:...`, `paypause:<id>`, `delgoal:<id>:...`,
`payrem:<id>:...`), прочитать/изменить/удалить чужую запись.

| Callback | Хендлер | Проверка владельца |
| --- | --- | --- |
| `undo:<id>` | `handlers/textFlow.ts` | `DELETE ... WHERE id=$1 AND user_id=$2` |
| `paypause:<id>` | `features/payments.ts` | `UPDATE ... WHERE id=$1 AND user_id=$2` |
| `delpay:<id>:yes\|no` | `features/payments.ts` | `DELETE ... WHERE id=$1 AND user_id=$2` |
| `payrem:<id>:record\|skip` | `features/payments.ts` | `findPayment(ctx.from.id, id)` + напоминание изначально отправлено только владельцу |
| `delgoal:<id>:yes\|no` | `features/goals.ts` | `UPDATE ... WHERE id=$1 AND user_id=$2` |
| `cat:<index>` | `handlers/textFlow.ts` | не id в БД — индекс в `flow.categoryOptions`, привязанном к `flows.get(uid)` в памяти процесса |

Ни один callback-хендлер не выполняет `WHERE id=$1` без `AND user_id=$2` — подбор чужого
id по возрастающей нумерации не даёт доступа к чужим данным.

## admin-only действия

Единственные административные действия — `action:restart` (`handlers/menuActions.ts`) и
`/health` (`features/health.ts`, добавлена в MKB-016). Обе используют одну и ту же
проверку: `ADMIN_TELEGRAM_ID` из `.env`, `ctx.from.id` должен строго совпадать; при
несовпадении — отказ без утечки того, что команда вообще существует для админа.

## Идемпотентность повторных callback/update

| Действие | Защита |
| --- | --- |
| Сохранение операции (`flow:save`) | `flows.delete(uid)` — синхронно, до первого `await`; повторный/гоночный callback не находит pending flow → отказ, без повторной вставки |
| Отмена операции (`undo:<id>`, `undocmd:<id>:yes`) | `DELETE ... WHERE id=... RETURNING *` — второй вызов находит 0 строк, явно сообщает «уже отменено» |
| Удаление платежа/закрытие цели (`delpay`, `delgoal`) | `DELETE`/`UPDATE ... WHERE active` — второй вызов находит 0 строк |
| Напоминание о платеже (`payrem:<id>:record`) | `last_notified` не даёт планировщику прислать повторное напоминание в тот же день; сам тап дополнительно защищён `Set<number>` от гонки одновременных callback |
| Навигация по меню (`menu:*`, `dash:*`, `stats:*`, `trend:*`) | Idempotent by construction — рендерят состояние заново, без побочных эффектов |

Все перечисленные случаи подсчитываются в `src/metrics.ts` (`recordIdempotentGuardHit`)
и видны через `/health`.

## Утечка чувствительных данных в ошибках

`src/middleware/safe.ts` классифицирует пойманную ошибку (`messageForError`) и **никогда**
не показывает пользователю сырой текст исключения — только один из трёх фиксированных
текстов (ошибка пользователя / временный сбой БД / обобщённая ошибка). Само исключение
целиком уходит только в `logger.error`, который дополнительно редактирует секреты
(`BOT_TOKEN`, `postgres://...` — `src/logger.ts`). Покрыто тестом:
`src/middleware/safe.test.ts` — включая кейс "SQL-ошибка с паролем в тексте не должна
попасть в ответ пользователю".

## Вне объёма (сознательно)

- Полноценные E2E на тестовой Postgres (testcontainers или аналог) — требует отдельной
  инфраструктуры, решено с пользователем не делать в рамках этой задачи.
- Нагрузочное/конкурентное тестирование (два пользователя одновременно в реальной БД) —
  без тестовой БД не автоматизировать; код-ревью показывает, что все запросы уже
  scoped по `user_id`, поэтому параллельные пользователи структурно не пересекаются.
- CI — в проекте нет настроенного CI-раннера; `npm run check` — команда, которую туда
  нужно будет воткнуть, если/когда CI появится.
